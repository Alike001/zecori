## Current assessment

Zecori now uses pinned `@noir-wallet/sdk` 0.1.9 to detect Noir Wallet, silently restore only an existing site authorization, request account consent from an explicit Connect click, read the authorized account's local balance summary, and invalidate readiness after an account change or timeout. Wallet data stays in browser memory. The first linked funded test remains **NO-GO**: Zecori does not import, unlock, fund, sign with, or broadcast through Noir Wallet.

<DocNotice title="Testnet build only" tone="safe">
  Noir distributes separate mainnet and testnet extensions. Compatibility work must use the official asset whose filename ends in `-testnet.zip`, loaded into a fresh browser profile with a newly created, unfunded test-only wallet. Never reuse an existing profile or recovery phrase.
</DocNotice>

## v1.0.40 changes relevant to Zecori

- The full quoted recipient is visible before confirmation and long addresses remain readable while the confirmation control stays available. This supports Zecori's exact-recipient review requirement, but Zecori has not independently accepted the flow.
- Recovery words remain outside readable page content and the accessibility tree until the user deliberately reveals them.
- Synchronization pauses are respected during transaction preparation, reducing competing balance and history work.
- Wallet cleanup, dApp approval handling, and response timeouts were hardened.

The release still excludes cross-restart transaction recovery and automatic resend. A funded Shield Funds stall has not been fully reproduced or verified as resolved.

## Implemented connection boundary

Provider detection uses the SDK's `getNoirWallet()` / `detectProvider()` path and does not connect an account. Startup calls `getAccounts()` silently. It reads `getBalance(account.id)` only when the origin already has authorization. `connect()` runs only from the consumer's Connect click. The integration never calls address enumeration, max transfer, signing, shielding, disconnect, or transaction methods.

The pinned SDK exposes `isNoirWallet`, extension `version`, and the Zcash API. The checksum-verified v1.0.40 testnet artifact injects exactly those fields; it does not inject its manifest name, extension ID, network, build digest, or pool. Mainnet and testnet artifacts both report version `1.0.40`. Zecori therefore treats the version as API compatibility evidence only and never derives network or Ironwood from an address.

The Move flow distinguishes shielded total, available total, pending total, synchronization, and insufficiency without storing or transmitting those values. A sufficient-looking balance is provisional because the current SDK result does not provide an Ironwood-specific spendable amount. The browser option therefore reports an honest unsupported configuration and cannot satisfy route readiness. The Base Sepolia connected and manual-recipient paths are unchanged.

A separate review-only payment model binds the order ID, exact `0.01` TAZ amount, dedicated receiver, expiry, destination, provider, and immutable route terms to a future request whose funding source can only be `shielded`. It rejects transparent funding. No wallet method receives this object and the send control is disabled.

## Safe testnet-only SDK path

This is an acceptance path, not permission to enable the integration:

1. Pin the official prerelease tag, testnet ZIP, `SHA256SUMS`, and build-provenance asset. Verify both the published digest and source commit before loading the extension.
2. Use a fresh disposable browser profile and a newly generated, unfunded test-only wallet. No production profile, existing recovery phrase, mainnet build, or reusable secret may enter the test environment.
3. Add a narrow adapter that detects the provider without connecting. It may call silent `zcash_getAccounts` only after an existing user authorization. It must never call a signing, sending, shielding, balance, address-enumeration, or disconnect method during detection.
4. Require an independently reviewable attestation for the exact testnet build and Ironwood-compatible shielded account. Address shape alone is not network or pool evidence. If either fact is missing, keep the option disabled.
5. Preserve explicit user control. A future source payment must be initiated and confirmed inside Noir only after Zecori publishes an operator-accepted, time-bounded shielded receiver. Zecori must never trigger an automatic spend.
6. Require a direct Ironwood shielded output to the dedicated receiver. Do not create or suggest a transparent intermediate transfer, transparent self-send, or browser-side shielding detour.
7. Keep secrets inside the wallet boundary. Zecori must never receive or log a recovery phrase, spending key, viewing key, raw transaction, or wallet database. Test telemetry may record only method names, result classes, build identity evidence, and redacted timestamps.
8. Independently verify the exact output, amount, receiver allocation, confirmations, and absence of a transparent intermediate hop using a separately authorized testnet verifier. UI state or wallet success text is not settlement evidence.
9. Record negative evidence for rejection, timeout, network/build mismatch, account change, and extension restart. No retry may spend automatically, and uncertain outcomes must stop for manual reconciliation.
10. Enable the adapter only after the isolated evidence is reviewed, the production build contains the approved adapter, and a second reviewer confirms that route and liquidity gates still default off.

## Isolated browser procedure

1. Download the official v1.0.40 testnet ZIP, checksum, and build provenance from the maintainer release.
2. Verify the checksum before extraction; do not use GitHub-generated source archives as extension packages.
3. Launch Chrome with a new temporary `--user-data-dir`; load only the unpacked testnet extension.
4. Create a new unfunded test-only wallet. Write its new recovery phrase offline for disposal; never import an existing phrase.
5. Open only the local Zecori origin and run the read-only compatibility smoke.
6. Confirm the request ledger contains detection and, if already authorized, `zcash_getAccounts` only.
7. Delete the temporary browser profile after evidence capture. Do not exercise Send, Shield Funds, Swap, signing, or broadcasts.

# Persistent disabled test-only variable quotes

Status: implemented for isolated tests only. The public product, API, fixed route, Render configuration, and settlement workflow do not use this module.

`server/test-variable-quote.ts` remains the only pricing implementation. It uses decimal strings parsed to `bigint`; floating-point amounts are rejected. `server/postgres-test-variable-quote.ts` adds persistence and calls that same implementation rather than copying the arithmetic. A quote requires an independently authorized provider approval containing a rational atomic rate, approval window, disclosed fees, minimum destination, source range, and destination-liquidity capacity. No market-reference lookup exists.

Rounding is deterministic: gross destination atomic units round down, the basis-point fee rounds up, and the fixed destination-atomic fee is added afterward. Migration 011 stores immutable rate approvals and quote bindings. Migration 012 additionally requires a real owner-bound `AWAITING_OPERATOR` request, its confirmed disabled-route destination intent, and a verified wallet-control proof; it rejects a mismatch in owner, request, intent, recipient fingerprint, chain, token, source amount, destination amount, or approval ID. Migration 013 separates the payment deadline from a four-hour confirmation/recovery window, binds the dedicated source receiver allocation, and permits only the rate transition `APPROVED -> REVOKED` with append-only history. Revocation blocks new quotes but does not erase or release existing obligations. Each PostgreSQL transaction locks the approval and owner/request rows, releases only unpaid expired reservations, checks all live liabilities, and inserts at most one quote for an order. This serializes multiple application processes and survives crashes/restarts without over-reserving liquidity.

The reservation binds quote ID, UUID order with a database foreign key to the owner request, owner UUID, destination-intent UUID and proof, exact source zatoshis, dedicated receiver/diversifier/activation height, exact post-fee USDC atomic units, strict EIP-55 recipient, Base Sepolia chain `84532`, official Circle test-USDC `0x036CbD53842c5426634e7929541eC2318f3dCF7e`, provider/rate approval, fee terms, minimum destination, liquidity, creation time, payment deadline, and confirmation deadline. A detected canonical Ironwood output becomes a durable liability and is never released while confirmations accumulate. Consumption re-runs independent verification for the exact order-bound output at ten confirmations; a caller-supplied amount is not settlement evidence. Late detection after cleanup, confirmation timeout, or a reorganization enters recovery/refund state rather than authorizing payout. Underpayment, exact payment, and overpayment are distinct outcomes. Consumed liquidity stays allocated and duplicate consumption fails. Migration 012 also rejects a future Base signing packet when a quote exists but is not consumed or its chain, token, recipient, or atomic payout differs. Packet persistence additionally requires an unexpired, one-time consumed payout authorization. The public acceptance path still rejects the disabled variable route.

The first illustrative approval fixture uses one destination atomic unit per source zatoshi, a 25 bps fee rounded up, and a fixed fee of 7 USDC atomic units:

| Source | Source zatoshis | Gross USDC atomic | Fee atomic | Exact destination atomic |
| --- | ---: | ---: | ---: | ---: |
| 0.01 TAZ | 1,000,000 | 1,000,000 | 2,507 | 997,493 |
| 0.02 TAZ | 2,000,000 | 2,000,000 | 5,007 | 1,994,993 |
| 0.05 TAZ | 5,000,000 | 5,000,000 | 12,507 | 4,987,493 |

The module labels every result as an `operator-approved-test-rate-not-market-price`. It does not fetch a price, assert market value, allocate a wallet address, create an order, publish instructions, sign, broadcast, or pay out.

Disposable PostgreSQL tests cover the three explicitly labelled testnet amounts, deterministic fee rounding, exact integers, insufficient liquidity, concurrent reservations, restart persistence, unpaid expiry release, detected-payment retention, ten-confirmation delay, late payment, source reorganization, immutable rate revocation history, under/overpayment, wrong chain, and duplicate consumption. The existing settlement tests separately cover owner binding, wallet-control proof replay, relay retry/replay, one-time payout approval, exact payout amount/recipient evidence, unresolved/refund states, and authenticated receipt recovery.

Provider-signature verification, authenticated owner-facing quote API integration, signer-side payout execution, and live end-to-end evidence remain blocked. The public UI/API must stay fixed-route and disabled until those gates pass and a separate release explicitly enables them.
